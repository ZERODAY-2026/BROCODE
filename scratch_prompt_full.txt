### 2. PROJECT OBJECTIVE

DataMind is an AI-powered data analysis agent that allows users to ask questions about structured datasets using natural language.

Example questions:
- Which countries had the highest GDP growth in the latest available year?
- Compare population trends across the five most populated countries.
- What is the average value of this metric by year?
- Which categories have the largest increase over the selected period?
- Why did the result change when I selected a different year?
- Show me the actual records and SQL used to answer this question.

The application must retrieve and calculate answers from **real data at question time**. It must not rely on hardcoded answers, fabricated tables, simulated database calls, or an LLM pretending to have queried a database.

The core flow must be:

**Natural-language question → Gemma interpretation → schema-aware SQL generation → SQL validation → real Snowflake execution → result verification → evidence-backed answer.**

Gemma must perform meaningful work, and Snowflake must be genuinely used for data retrieval and computation.

### 3. NON-NEGOTIABLE TECHNOLOGY REQUIREMENTS

#### A. Snowflake — required

Use a real Snowflake database through the official Snowflake Python Connector.

The application must:
- Connect using credentials supplied through environment variables.
- Discover available databases, schemas, tables, columns, and data types within the configured permissions.
- Allow a user or administrator to configure the permitted dataset and schema.
- Generate queries based on the actual discovered schema.
- Execute validated queries against Snowflake when a question is asked.
- Retrieve real records and calculated results.
- Return query evidence, execution status, and relevant source information.
- Handle missing credentials, unavailable warehouses, permissions errors, empty results, timeouts, and connection failures.
- Use read-only, least-privilege database permissions wherever possible.

Do not substitute SQLite, CSV-only processing, local arrays, or mock responses for the required Snowflake execution.

CSV or public datasets may be used to prepare or load data, but the actual question-answering path must query Snowflake.

If Snowflake credentials are unavailable during development, build the genuine integration and clearly show that setup is required. Never claim that a live connection or query succeeded unless it actually did.

#### B. Google Gemma — required

Use a real Google Gemma model as a meaningful part of the application.

Prefer a practical local setup using **Gemma through Ollama**, provided a compatible Gemma model is available and the integration is verified. Keep the model configurable so the project can support another legitimate Gemma deployment if needed.

Gemma must contribute to meaningful tasks such as:
1. Interpreting the user's question.
2. Identifying relevant tables and columns from the discovered schema.
3. Producing a structured analysis plan or candidate SQL query.
4. Explaining verified query results in understandable language.
5. Identifying ambiguity and asking clarifying questions.
6. Explaining limitations when data is missing or cannot support a conclusion.

Do not use a generic LLM as an undisclosed replacement for Gemma. Do not hardcode Gemma responses or pretend the model was called.

Implement a dedicated Gemma service/adapter with configuration, timeout handling, model availability checks, structured output validation, and useful error messages.

The application must remain honest if Gemma is unavailable. It may show setup guidance, but must not silently fabricate AI-generated output.

### 4. REQUIRED FEATURES — M1 TO M8

Implement, test, and document every requirement below.

**M1 — Natural-language interaction**

Users must ask questions in ordinary language without writing SQL themselves. Support analytical questions such as filtering, grouping, sorting, aggregation, comparisons, and time-based analysis where the available data supports them.

**M2 — Real data retrieval at question time**

Every answer that claims to describe the dataset must be backed by a query executed against Snowflake at question time. Do not answer dataset questions from model memory or previously hardcoded outputs.

**M3 — Grounded answers**

The natural-language answer must be based on the actual query results. The model must not invent values, rows, percentages, dates, trends, or conclusions.

Use deterministic calculations for important numeric results whenever possible. Preserve numeric precision, units, filters, and date ranges.

If a claim cannot be supported by the returned data, do not make it.

**M4 — Explain the analysis**

For each answer, explain in clear language:
- What was measured.
- Which filters were applied.
- Which tables and columns were used.
- Which assumptions were made.
- Which time period or categories were included.
- Any limitations affecting the result.

If the question is ambiguous, ask a focused clarification question instead of making a risky assumption.

**M5 — Inspectable evidence**

Users must be able to inspect:
- The executed SQL query.
- The source table or tables.
- Relevant column names.
- The returned records or a useful preview.
- The number of rows returned.
- Applied filters and aggregation.
- Query execution status.
- A Snowflake query identifier when available.
- Relevant limitations and errors.

Never display generated SQL as executed SQL unless Snowflake actually executed it. Clearly distinguish a proposed query from an executed query.

**M6 — Ambiguity, missing data, and unsupported questions**

Handle:
- Questions with multiple reasonable interpretations.
- Missing tables or columns.
- Empty query results.
- Null values.
- Unsupported operations.
- Invalid or unsafe SQL.
- Excessively expensive queries.
- Database connection failures.
- Gemma failures or invalid model output.
- Requests that cannot be answered from the available dataset.

Explain the problem and, when possible, suggest a valid alternative. Do not invent an answer to fill the gap.

**M7 — Meaningful Snowflake and Gemma integration**

Both technologies must be genuinely involved in the primary application workflow.

Snowflake performs real data retrieval and calculations. Gemma interprets questions and helps produce or explain analysis. Neither integration may be a decorative feature.

**M8 — Reproducible open-source implementation**

A new developer must be able to understand, configure, run, test, and reproduce the project from the repository and README.

Include complete source code, dependency files, environment configuration examples, setup instructions, data attribution, architecture documentation, test instructions, and an appropriate open-source licence.

### 6. SAFE SQL EXECUTION

Treat model-generated SQL as untrusted input.

Implement a dedicated SQL validation layer before every execution.

At minimum:
- Allow only a single read-only `SELECT` query, including safe CTEs where supported.
- Reject destructive or mutating statements such as `INSERT`, `UPDATE`, `DELETE`, `DROP`, `ALTER`, `CREATE`, `TRUNCATE`, and other unauthorized operations.
- Reject multiple statements and attempts to bypass the permitted query scope.
- Validate tables and columns against the discovered schema and configured permissions.
- Restrict queries to explicitly permitted databases, schemas, and tables.
- Apply a configurable result-row limit.
- Apply statement timeouts and reasonable resource limits.
- Use parameter binding for user-supplied values whenever applicable.
- Do not treat a simple string check as the only SQL security mechanism.
- Do not let the model choose unrestricted database credentials or expand its own permissions.
- Return safe, understandable errors without exposing credentials or sensitive internal details.

Use database-side permissions as an additional security boundary. A read-only application validator is not a substitute for least-privilege database access.

Record the SQL that actually ran and its execution status.

### 7. RESULT VERIFICATION AND HALLUCINATION PREVENTION

Create a structured response format between the backend and frontend.

The response should contain appropriate fields for:
- User question.
- Answer status.
- Natural-language answer.
- Executed SQL, if execution occurred.
- Source tables and columns.
- Returned result rows or preview.
- Row count.
- Query identifier, if available.
- Filters and assumptions.
- Warnings and limitations.
- Clarification request, if needed.
- Error details safe for display.

Verify the model's explanation against the actual results before returning it.

Do not allow Gemma to alter database values, invent additional records, or describe calculations that were not performed.

For important numerical answers, derive totals, averages, rankings, and percentages from actual query results or verified database calculations. Clearly explain the denominator and comparison period when relevant.

If a response cannot be verified, mark it as incomplete or unsupported instead of presenting it as a fact.
